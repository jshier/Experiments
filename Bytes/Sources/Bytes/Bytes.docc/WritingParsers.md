# Writing a parser

Turn a binary format's specification into a parser and a serializer that run at memory speed.

## Overview

This guide builds both directions for a small, made-up sensor format, then covers streams and lists the
rules that keep `Bytes` code fast. The goal is parsing code that says what the format says: field names and
the types you compute with, and no `UInt8`, bit numbers, or shifts except for a value that really is one.

| Field | Size | Notes |
|---|---|---|
| Signature | 2 bytes | `0x53 0x52` ("SR") |
| Version | 4 bits | currently 1 |
| Unit | 2 bits | 0 Celsius, 1 Fahrenheit, 2 Kelvin |
| Has timestamp | 1 bit | |
| Reserved | 1 bit | 0 |
| Sample count | 2 bytes | |
| Timestamp | 8 bytes | only if the flag is set |
| Samples | 3 bytes each | signed 24-bit values |
| Sensor ID | 6 bytes | an opaque identifier |

All integers are big-endian.

### Pick a cursor

The first choice is which cursor to read and write with. They have the same byte-level calls; they differ in
what else they know:

| Format | Cursor |
|---|---|
| Fields cross byte boundaries in the stream (a 3-bit field, then a 12-bit one) | ``BytesReader``, ``BytesWriter`` |
| Whole bytes, mixed byte orders, or a byte order you pass at each call | ``AlignedBytesReader``, ``AlignedBytesWriter`` |
| Whole bytes, one byte order for the integers | ``BigEndianBytesReader``, ``LittleEndianBytesReader`` and their writers |

Most formats are the second or third kind: flags *inside* a byte don't make a format bit-addressable, because
you read the ``Byte`` and take its fields apart by name (below). The byte-ordered cursors read and write
integers by type, `read(UInt32.self)` and `write(length)`, in the cursor's order, so no call repeats it. The
sensor format is big-endian throughout and has only whole-byte fields in its stream, so it uses
``BigEndianBytesReader`` and ``BigEndianBytes`` writers. (Only the bit-addressable cursors have bit-level
API: ``Bits`` reads and writes, `seek(toBitPosition:)`, and `skip(bitCount:)`. Convert at a byte boundary with
`BytesReader(alignedReader)`.)

### Name the fields

Pick each field's type from its meaning, and name the bits inside a byte once:

- Flags and packed fields inside a value are a struct generated by `@BitFields` (below), or ``BitFlag``,
  ``BitField``, and ``BitPattern`` descriptors used by hand.
- Multi-byte integers are read as the integer they are: `read(UInt16.self)` on a byte-ordered cursor, or
  `read(Int.self, as: Byte3.self)` for an odd width such as a 24-bit length. ``ByteGroup`` (``Byte2`` through
  ``Byte16``) names the width in the stream; the integer type is the one your code computes with.
- Fields that are really enumerations are enums with integer raw values, read through their field.
- Opaque fixed-size values (addresses, identifiers, digests) are your own types conforming to
  ``ByteRepresentable``, backed by an `InlineArray` of their bytes.
- A fixed run of fields is a record (below), read in one call with one bounds check.

A `UInt8` belongs in parsing code only when the byte is the number: a length or a count
(`read(UInt8.self)`). A byte of flags is a ``Byte`` with named flags; a byte of nothing in particular is
usually a field of a record.

### Records and the macros

Bits packed into a byte are declared once, with `@BitFields`, and a run of fixed fields with `@BinaryRecord`.
The macros are in their own product, **`BytesMacros`**: add it to your target's dependencies and
`import BytesMacros` (which re-exports `Bytes`). The core `Bytes` product has no macro dependency (and so no
swift-syntax build); everything the macros generate can be written by hand with the protocols and descriptors
in `Bytes`, shown below.

```swift
import BytesMacros

enum Unit: UInt8 { case celsius, fahrenheit, kelvin }

@BitFields(Byte.self, reserved: 0...0)
struct SensorFlags {
    @Field(bits: 4...7) var version: Int
    @Field(bits: 2...3) var unit: Unit          // an enum with integer raw values
    @Flag(bit: 1) var hasTimestamp: Bool
}

@BinaryRecord(.bigEndian)
struct SensorHeader {
    @Field(Byte2.self, expecting: 0x5352) var signature: UInt16   // a magic number: must match
    var flags: SensorFlags                                        // a @BitFields type, or another record
    @Field(Byte2.self) var sampleCount: Int
}
```

`SensorFlags` reads and writes one byte, throws ``BytesError/invalidValue`` for a reserved bit that's set or
a unit with no case, and each field compiles to the shift and mask you'd write by hand. `SensorHeader` reads
its 5 bytes with one bounds check, then each field from a cursor whose length the optimizer knows, and
consumes nothing if any of them throws. Both are ``BinaryParsable``, ``BinaryWritable``, and
``FixedSizeBinary``: `reader.read(SensorHeader.self)` and `writer.write(header)`.

A record's fields can be single bytes (`@Field(Byte.self) var bitDepth: UInt8`), bytes it skips
(`var unused: Padding<Byte2>`), or bytes that must be zero (`var reserved: Reserved<Byte3>`); the last two
store nothing. A format that names its byte order in its first bytes, as ELF and PCAPNG do, declares its
records without one, `@BinaryRecord`, and reads them from a generic parser specialized for each order:

```swift
@BinaryRecord                                   // in the byte order of the cursor that reads it
struct SectionHeader {
    @Field(Byte4.self) var name: UInt32
    @Field(Byte4.self) var type: SectionType
    @Field(Byte8.self) var offset: UInt64
}

func parse<Mode: ByteOrderedCursorMode>(_ reader: inout GenericBytesReader<Mode>) throws(BytesError) -> SectionHeader {
    try reader.read(SectionHeader.self)
}
let header = switch byteOrder {
case .littleEndian: var reader = LittleEndianBytesReader(data); try parse(&reader)
case .bigEndian: var reader = BigEndianBytesReader(data); try parse(&reader)
}
```

Such a record is ``ByteOrderedParsable``: only byte-ordered cursors read it, so a cursor whose order isn't known
is a compile error rather than a guess.

### Parse

Create a cursor over the input and read the fields in order. A function that reads part of a message takes
the cursor `inout`; since it's `~Escapable`, say how the result's lifetime relates with `@_lifetime` (this
needs the `Lifetimes` experimental feature in your target).

```swift
struct SensorID: ByteRepresentable {
    var rawBytes: InlineArray<6, UInt8>
    init(rawBytes: InlineArray<6, UInt8>) { self.rawBytes = rawBytes }
}

struct Reading {
    var unit: Unit
    var timestamp: UInt64?
    var samples: [Int32]
    var sensor: SensorID
}

enum ReadingError: Error { case truncated, malformed }

func parseReading(_ data: RawSpan) throws(ReadingError) -> Reading {
    do throws(BytesError) {
        var reader = BigEndianBytesReader(data)

        let header = try reader.read(SensorHeader.self)
        guard header.flags.version == 1 else { throw .invalidValue }
        let timestamp = header.flags.hasTimestamp ? try reader.read(UInt64.self) : nil

        // A run of values: one bounds check, then a vectorized loop.
        var samples: [Int32] = []
        samples.reserveCapacity(header.sampleCount)
        var run = try reader.readSection(byteCount: header.sampleCount &* 3)
        run.forEach(Byte3.self) { sample in
            samples.append(sample.signedInteger(.bigEndian, as: Int32.self)) // 24-bit, sign-extended
        }

        let sensor = try reader.read(SensorID.self)
        return Reading(unit: header.flags.unit, timestamp: timestamp, samples: samples, sensor: sensor)
    } catch {
        throw error == .insufficientData ? .truncated : .malformed
    }
}
```

Errors are typed (``BytesError``), so mapping them to your own costs nothing, and a read that throws
consumes nothing: after `.insufficientData` a streaming caller can wait for more data and retry from the
same position. Counts and lengths read from the data may be any integer type: `readSection(byteCount:)`,
`read(byteCount:)`, and `skip(byteCount:)` take them as they are (a `UInt64` size needs no `Int(…)` that
could truncate), and reject a negative one.

### Serialize

Write a new array with `[UInt8](byteCapacity:mode:writing:)` (or append to one with
`append(byteCapacity:writing:)`), which keeps exactly the bytes written; `withBytesWriter` does the same for
any `OutputSpan<UInt8>`. The `mode:` argument picks the cursor: `BigEndianBytes.self` here;
`[UInt8](alignedByteCapacity:writing:)` gives an ``AlignedBytesWriter``, and `[UInt8](byteCapacity:writing:)`
a bit-addressable one. Annotate the closure's error type, as below: unannotated, it throws `any Error`.
Lengths that prefix their data are usually known before writing; compute them first.

```swift
func serialize(_ reading: Reading) throws(BytesError) -> [UInt8] {
    let size = 5 + (reading.timestamp == nil ? 0 : 8) + reading.samples.count * 3 + 6
    return try [UInt8](byteCapacity: size, mode: BigEndianBytes.self) { (writer) throws(BytesError) in
        try writer.write(SensorHeader(
            flags: SensorFlags(version: 1, unit: reading.unit, hasTimestamp: reading.timestamp != nil),
            sampleCount: reading.samples.count))
        if let timestamp = reading.timestamp {
            try writer.write(timestamp)
        }
        // A generating write: the closure is fused into one vectorized loop, and keeps each value's low
        // 3 bytes, so negative samples come out as 24-bit two's complement.
        try writer.write(Byte3.self, .bigEndian, count: reading.samples.count) {
            UInt32(bitPattern: reading.samples[$0])
        }
        try writer.write(reading.sensor)
    }
}
```

The record's expected signature is its default, so the memberwise initializer doesn't take it. On a
byte-ordered writer a bare integer literal doesn't compile (it could be a ``Byte``, a `UInt8`, or an `Int8`):
state the width, as `UInt16(1)` or `1 as UInt16`.

### The same format by hand

Without the macros, declare each field once as a descriptor and use it by name at every read and write.
Declare descriptors as computed `static var`s: each use then inlines to the shift and mask you'd write by hand
(a `static let` is a lazily initialized global, checked on every access).

```swift
enum SensorFlagFields {
    static var version: BitField<Int> { BitField(bits: 4...7) }
    static var unit: BitField<Unit> { BitField(bits: 2...3) }
    static var hasTimestamp: BitFlag { BitFlag(bit: 1) }
    static var reserved: BitFlag { BitFlag(bit: 0) }
}

func readFlags(_ reader: inout BigEndianBytesReader) throws(BytesError) -> (version: Int, unit: Unit, hasTimestamp: Bool) {
    let flags = try reader.read(Byte.self)
    try flags.requireClear(SensorFlagFields.reserved)                  // reserved bits are 0
    return (flags[SensorFlagFields.version],
            try flags.value(of: SensorFlagFields.unit),               // throws for a unit with no case
            flags[SensorFlagFields.hasTimestamp])
}

func writeFlags(_ writer: inout BigEndianBytesWriter, unit: Unit, hasTimestamp: Bool) throws(BytesError) {
    try writer.write(Byte {
        $0[SensorFlagFields.version] = 1
        $0[SensorFlagFields.unit] = unit
        $0[SensorFlagFields.hasTimestamp] = hasTimestamp
    })
}
```

``BitFlag`` and ``BitField`` count bits from the least significant, as `[bit:]` does; the
`bitFromMostSignificant:` and `bitsFromMostSignificant:` forms count from the other end, for specifications
that draw bit 0 on the left. ``BitPattern`` checks fixed bits at once with the pattern written as the
specification draws it: `flags.matches("0001_??0?")`. The same subscripts work on any integer: a DOS date
read as a `UInt16` takes its fields as `date[DOSDate.month]`.

A record by hand is a type with `init(parsing:)` and `write(to:)`: that is all ``BinaryParsable`` and
``BinaryWritable`` ask for, generic over the cursor's mode so one implementation serves every cursor.

```swift
struct Version: BinaryParsable, BinaryWritable {
    var major: UInt8, minor: UInt8
    init(major: UInt8, minor: UInt8) { (self.major, self.minor) = (major, minor) }
    init<Mode: BytesCursorMode>(parsing reader: inout GenericBytesReader<Mode>) throws(BytesError) {
        major = try reader.read(UInt8.self)       // these bytes are the numbers
        minor = try reader.read(UInt8.self)
    }
    func write<Mode: BytesCursorMode>(to writer: inout GenericBytesWriter<Mode>) throws(BytesError) {
        try writer.write(major)
        try writer.write(minor)
    }
}
```

### Variable-size parts

Many formats prefix a part with its length: a string, a list, a nested message. Read the part as a
section, a cursor of its own that every read inside is bounded to, and check it was fully consumed:

```swift
var message = try reader.read(sectionPrefixedBy: LEB128.self, maxByteCount: 4)
let topic = try message.read(utf8PrefixedBy: Byte2.self)     // a validated UTF8Span
let retained = try message.read(UInt8.self)
try message.expectEnd()                                       // .trailingData otherwise
```

(On a byte-ordered cursor the length types need no order; on an aligned one, pass it: `Byte2.self,
.bigEndian`.) These reads are atomic too: if the section isn't all there, nothing is consumed, not even its
length. To write one, compute its size first and write the length directly, or let a section writer fill it
in:

```swift
try writer.write(UInt64(size), as: LEB128.self)
try writer.write(sectionPrefixedBy: Byte2.self) { (section) throws(BytesError) in
    try section.write(topic, prefixedBy: Byte2.self)
}
```

Lengths computed from the data (a block's length less its header) can come out negative: reading a section or
bytes of a negative length throws ``BytesError/invalidValue``, as any malformed length does, so the
subtraction needs no guard of its own. Other parts are found by what ends them, or have widths the data names:

```swift
let name = try reader.read(utf8TerminatedBy: 0)                      // a C string, validated
let offset = try table.read(Int.self, byteCount: trailer.offsetSize)  // 1 through 8 bytes, chosen at run time
try options.forEachRecord(tag: Byte2.self, length: Byte2.self, paddedTo: 4) { (code, value) throws(BytesError) in
    …                                                                 // each value padded to 4 bytes
}
```

### Text inside binary formats

Tags, signatures, and numbers written as digits have their own reads, written the way that compiles best, so a
parser needs no hex constants or bit tricks for them:

```swift
try reader.expect(Byte4(ascii: "qoif"))                 // a signature, as its characters
switch try reader.read(Byte4.self) {                    // a PNG chunk type
case Byte4(ascii: "IHDR"): …
case Byte4(ascii: "IEND"): …
default: …
}
try reader.expect(0x184D_2204 as UInt32, .littleEndian) // a magic number as the specification writes it

let year = try reader.read(Int.self, asciiDigits: 4)    // "2026": one load, checked and combined at once
try reader.expect(Byte(ascii: "-"))
try writer.write(month, asciiDigits: 2)                 // "07"
```

``ByteGroup/init(ascii:)`` folds to the integer you'd otherwise write in hex, in memory order (use it where it's
evaluated, or in a computed property; a `static let` of it is initialized lazily). Single bytes have character
classes as `UInt8` properties (`isASCIIDigit`, `asciiDigitValue`, `asciiHexDigitValue`, `isASCIIWhitespace`,
`asciiLowercased`), each a subtraction and one unsigned compare with no branch, and
``ByteLanes`` has the same classes for 16 bytes at once (``ByteLanes/asciiDigits``,
``ByteLanes/matching(in:)``, ``ByteLanes/matching(_:)-(Unicode.Scalar)``), with no per-lane comparisons.

### Parse each value once

A parser that validates a structure and a caller that then walks it decode every value twice. MQTT's
properties were: `MQTTPublish` checked its property list when parsed, and the caller iterated the same bytes
again to use them. Let the parser hand each value to a closure as it validates it, so the one pass does
both:

```swift
struct Property { var id: UInt8; var value: UInt32 }

func parseProperties(
    _ reader: inout BigEndianBytesReader, visiting visit: (Property) -> Void
) throws(BytesError) -> Int {
    var properties = try reader.read(sectionPrefixedBy: Byte2.self)
    var count = 0
    while !properties.isAtEnd {
        let property = Property(id: try properties.read(UInt8.self), value: try properties.read(UInt32.self))
        visit(property)               // used while it's decoded: nothing is parsed a second time
        count += 1
    }
    return count
}
```

Keep a plain path too, if callers often don't want the values: a separate body for each (not a plain call
through an empty closure) measured the plain path unchanged and the visiting one 16.6% cheaper than parsing
and then iterating.

### Streams: pipelines and `BytesAsync`

A stream is processed in pieces, and a message's pieces go through stages: compress, encrypt, frame.
A ``ByteTransform`` is one stage (input span in, output span out, flush semantics like zlib's), and
`then(_:)` composes stages into a ``Pipeline`` that allocates its buffer once. The drive loop
``ByteTransform/transform(_:appending:flush:growth:)`` runs a stage until it has taken all its input:

```swift
import BytesCompression

func gzip(_ message: [UInt8]) throws(BytesError) -> [UInt8] {
    var encoder = DeflateEncoder(format: .gzip, level: 6)
    var compressed: [UInt8] = []
    let progress = try encoder.transform(message.span.bytes, appending: &compressed, flush: .finish)
    precondition(progress.status == .finished)    // every stage ends the same way at `.finish`
    return compressed
}
```

Stages declare their units (``ByteTransform/maximumUnitByteCount``: the most input one needs at once, a TLS
record's 16,645 bytes; ``ByteTransform/minimumOutputCapacity``) and pipelines size their buffers from them.
A stage returns ``TransformStatus/finished`` at `.finish` once its output is delivered, or throws if its
input ended early (a decoder's truncated stream), so a loop stops at `.finished` and `.needsInput` only
means "more input, please".

Where the input arrives over time, from a socket, use the `BytesAsync` product: ``ByteBuffer`` gets
`receive` (the asynchronous `fill`, for a read that suspends), and `AsyncByteTransform` is
`ByteTransform` with `async` calls. Any stage becomes one with `synchronously()` (calls run in place) or
`offloaded(to:)` (calls run on a Dispatch queue, so a heavy compressor doesn't hold a thread of Swift's
cooperative pool); the parallel codecs have `async` entry points the same way.

```swift
import BytesAsync
import Dispatch

func gzip(_ message: [UInt8]) async throws(BytesError) -> [UInt8] {
    var stage = DeflateEncoder(format: .gzip, level: 9).offloaded(to: .global(qos: .utility))
    var compressed: [UInt8] = []
    _ = try await stage.transform(message.span.bytes, appending: &compressed, flush: .finish)
    return compressed
}
```

### Keep it fast

- **Keep cursors local, or pass them `inout` to inlinable code.** A cursor passed `inout` to a closure
  or function the compiler doesn't inline lives in memory: every read then loads and stores its offset,
  and loops stop vectorizing. Most parsers are a few local functions in one module, which is fine.
- **Read fixed-size records as one value or a sub-cursor** (`read(SensorHeader.self)`, or
  `try reader.readSection(byteCount: n)`). Their bounds checks fold to one per record.
- **Loop over runs with `forEach`, generating writes, or bulk reads/writes**, not field by field with
  calls the compiler can't see through. Plain loops of single reads and writes also vectorize when the
  cursor is local.
- **Bits one at a time are inherently sequential.** For runs of bit fields, use `forEach(Nibble.self)` or
  `write(Nibble.self, count:)`, which work a byte or block at a time.
- **Fields that fill a byte: read the `Byte`, then take it apart by name.** Each sub-byte read
  (`read(Bool.self)`, `read(Crumb.self)`, …) takes the general bit path, a bounds check, a two-byte window,
  and an advance, even at a byte boundary. Read the whole ``Byte`` once and use its fields (a `@BitFields`
  struct, or `flags[SensorFlagFields.unit]`), and build a `Byte` before writing it. In MQTT's flag bytes that
  was a third of the code, and 15.6% of the whole parse.
- **Name the order once.** A byte-ordered cursor compiles to the same code as an aligned one passing the
  order at each read. Little-endian is free on Apple platforms; big-endian adds a byte swap, which vectorizes.
- **`for`-`in` works** (``BytesReader`` and its `values(of:_:)` views are `Iterable`; declare the reader
  with `var`, and bind a view to a constant before looping), but typed views decode into a buffer first.
  For power-of-two widths `forEach` is about 2.5x faster; for 3-, 5-, 6-, and 7-byte groups `for`-`in` is
  as fast, or faster (3 bytes). For bytes, or 4-byte custom types, iterate zero-copy spans: `for byte in
  reader`, or `reader.read(InlineArray<4, UInt8>.self, count:)`.
- **Measure.** `Benchmarks/BytesBenchmarks` shows how to benchmark against hand-written code and record
  bandwidth, and `Benchmarks/RESULTS.md` records what each choice in this library cost or saved.
